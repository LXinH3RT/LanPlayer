# 安全边界

## 1. 威胁模型

这个 App 的目标场景是**家庭局域网**：同一网段内的手机连接家里 Windows 上的共享。
它不打算穿越公网、不打算多租户隔离，也不承诺抵抗已经拿到设备 root/越狱权限的攻击者。

明确的假设：

* 局域网内可能有陌生设备（访客 Wi-Fi、被入侵的 IoT），因此**共享凭据必须够强**，
  不能是 6 位数字口令。
* SMB 流量默认未加密（SMB3 加密需要服务端显式开启），同网段的被动嗅探能看到内容。
* 手机可能丢失，因此本地存储的凭据要有清晰的失效手段（改密码 / 吊销账号即可）。

## 2. 凭据形态

分享就是**普通的 SMB 账号**，本项目不定义任何自定义协议、不生成凭据、不做密码派生：

* 共享与账号由用户在 Windows 上自行创建（「文件共享」或 `New-SmbShare`），
  密码由用户自己决定，本仓库不提供也无法读取它。
* App 端只保存「地址 + 共享名 + 用户名 + 密码」这四项，直接交给 libsmb2
  做 NTLMSSP 认证。内核里没有任何密钥解析或密码派生逻辑。
* 强度取决于用户设置的密码本身。
* 轮换与吊销都在系统侧完成（改本地账号密码 / 删除共享权限），App 无需配合。

**已知弱点（有意接受）**：密码是完整凭据，谁看到谁就能读该共享。分享密码 = 分享读权限。
凭据以明文形式出现在聊天记录里，这是刻意的简化。

## 3. 本地存储

当前实现：

| 数据 | 位置 | 内容 |
|------|------|------|
| 服务器列表 | `<AppSupport>/lanplayer/servers.json` | 明文账号密码 |
| 设置 | `settings.json` | 无敏感信息 |
| 播放进度 | `progress.json` | 不含凭据的路径 + 位置 |

为什么存明文：SMB 认证需要一个可还原的密码，而不同平台的“保存密码”机制
（Keychain / Keystore）会让首次接入变复杂。这是**可改进项**，见 §6。

缓解措施：

* 文件位于应用私有目录（Android 内部存储 / iOS 沙盒 Documents 之外的 Application Support），
  其他 App 无法读取；
* 写入时先用探针验证目录可写，失败则换下一个候选目录，不会静默丢凭据；
* 应用没有导出/备份这些文件的入口；Android 的 `allowBackup` 默认受系统策略约束，
  若要严格可在清单里设 `android:allowBackup="false"`。

## 4. 传输

* 凭据通过 URL userinfo 或 `options_json` 传给内核，**只在内存里**。
* `lp_thread` 日志默认级别 INFO，不打印密码；`smb.c` 打印的是 `//host/share/path`。
* 目录列表返回的 `path` 不含凭据，避免凭据随 UI 状态扩散。
* SMB 签名：客户端 `SMB2_NEGOTIATE_SIGNING_ENABLED`，服务端要求签名时会自动签名。
  SMB3 加密需要服务端开 `EncryptData`，客户端目前不强制，属于局域网信任模型的一部分。

## 5. 服务端

本仓库**不包含任何服务端组件**（原先的 `server/lanplayer_share.py` 一键共享脚本已移除）。
共享完全由 Windows 自带能力提供，安全边界也在系统侧：

* 共享与账号由用户用「文件共享」图形界面或 `New-SmbShare` 自行创建，本仓库不介入。
* 建议给播放器单独建一个本地账号，且**只授予该共享的 READ**，不要加入管理员组。
* 吊销 = 在系统里删除共享权限或禁用账号，App 端无需配合。
* 共享权限一旦下发就等于读权限，不要把含敏感内容的目录整体共享出去。

## 6. 后续加固（roadmap）

1. 用 `flutter_secure_storage`（iOS Keychain / Android Keystore）替换明文文件。
2. 可选 SMB3 加密：服务端开启 `EncryptData` 后客户端自动协商。
3. 首次连接时做 TOFU 式指纹提示（显示服务端 SMB 签名证书/主机指纹），
   防止同网段 DNS 欺骗把客户端引到假服务器。
4. Android `allowBackup=false` + 文件级加密（EncryptedFile）。

## 7. 文档与仓库里的环境信息

这个仓库准备公开，所以**代码、脚本、文档、注释、commit message、截图里都不出现真实环境**。
不是洁癖：内网网段 + 设备清单 + 共享目录名 + 片单四样凑在一起，足以定位到具体的人和机器，
而这些东西对读者理解项目毫无帮助。口径：

| 类别 | 写什么 | 不写什么 |
|-|-|-|
| 主机地址 | `192.168.1.10`（RFC 5737 之外的私网示例）、`192.0.2.1` | 任何真实内网地址、真实网段 |
| 账号 / 密码 | `share` / `guest` | 真实 SMB 账号，尤其是拿它当密码用的那种 |
| 设备 | `Windows` / `Mac` / `iPad` / `Android 手机` | 具体型号、芯片、系统小版本、机型代号 |
| 设备标识 | `<UDID>` / `<TEAM_ID>` | 真实 UDID、开发者团队 ID、序列号 |
| 路径 | `/Users/me/...`、`C:\Users\me\...` | 真实用户名下的绝对路径 |
| 主机名 | `DESKTOP-FILE`、`nas` | 真实计算机名与 mDNS 广播名 |
| 素材 / 截图 | `scripts/make_doc_media.ps1` 造的合成彩条与静音音轨 | 真实影音画面、平台水印、片名与剧集标题 |

写新文档时用同一套占位值；重拍截图时先跑 `scripts/make_doc_media.ps1`，再用
`scripts/capture_screen.ps1 -Browse file:///<生成的目录>` 截。`tool/check_all.py` 的
`check_release_policy()` 会拦住「只对某一台机器适用的笔记类文件」入库，但**拦不住上面这些
真实值** —— 那些靠写的人自觉，PR 里看到就改。
